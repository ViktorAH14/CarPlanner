# CarPlanner

> Кроссплатформенное приложение для управления расходами на автомобиль: заправки, техническое обслуживание, ремонт, средний расход топлива и напоминания о сервисных работах.

## 🚀 О проекте

CarPlanner помогает пользователям отслеживать расходы на заправку, рассчитывать средний расход топлива, учитывать все расходы, связанные с автомобилем, и не пропускать сроки технического обслуживания благодаря умным напоминаниям.

Приложение поддерживает синхронизацию данных между всеми устройствами пользователя и работает в офлайн-режиме: все изменения сохраняются локально и отправляются на сервер при восстановлении интернет-соединения.

**Технологический стек:**

- **Фронтенд:** Flutter (Android, Windows, Linux) с дизайном Material 3
- **Бэкенд:** Node.js + Express + Sequelize
- **База данных:** PostgreSQL
- **Управление состоянием:** Riverpod (планируется на следующую итерацию)
- **Контейнеризация:** Docker & Docker Compose

## 📱 Особенности фронтенда (текущее состояние)

Фронтенд реализует чистую feature-ориентированную архитектуру с интерфейсом Material 3 и полным тестовым покрытием главного экрана.

**Ключевые возможности**

- **Главный экран** (`lib/features/home/presentation/home_screen.dart`): описательный заголовок, три карточки статистики (Топливо, Обслуживание, Ремонт и прочее) и кнопка «Добавить запись».
- **Адаптивная вёрстка:** используется `SingleChildScrollView` для корректного отображения на экранах разного размера.
- **Дизайн Material 3:** применяется `ThemeData(useMaterial3: true)` с seed-цветом для единого визуального стиля.
- **Виджет-тесты:** подробные тесты в `test/home_screen_test.dart` проверяют отрисовку интерфейса и взаимодействие (например, показ SnackBar при нажатии кнопки).
- **Готовность к документированию:** все публичные классы и методы снабжены комментариями Dart doc (`///`), совместимыми с генерацией `dart doc`.

**Как сгенерировать документацию фронтенда**

Из каталога `frontend/` выполните:

```bash
dart doc --open
```

Команда генерирует HTML-документацию в `CarPlanner/frontend/doc/api` и открывает её в браузере.

## 💻 Настройка окружения разработчика (бэкенд)

Бэкенд полностью контейнеризирован. Устанавливать Node.js или PostgreSQL локально не требуется.

### 1. Настройте окружение

Скопируйте шаблон и задайте свои значения:

```bash
cp .env.example .env
```

Обязательные переменные в `.env`:

| Переменная          | Описание                                   |
| ------------------- | ------------------------------------------ |
| `POSTGRES_USER`     | Имя пользователя PostgreSQL                |
| `POSTGRES_PASSWORD` | Пароль PostgreSQL                          |
| `POSTGRES_DB`       | Имя основной базы данных (`carplanner_db`) |
| `JWT_SECRET`        | Секретный ключ для подписи JWT-токенов     |

Docker Compose автоматически собирает `DATABASE_URL` и `TEST_DATABASE_URL` из этих значений. Не добавляйте строки подключения в `.env`.

### 2. Запустите весь стек (бэкенд + БД)

```bash
docker compose up
```

Сервер работает на порту **3000**. Отладчик Node.js доступен на порту **9229**.

При первом запуске Postgres создаёт обе базы — `carplanner_db` и `carplanner_test_db` — через init-скрипт в `docker/postgres/`.

### 3. Запустите тесты бэкенда

Тесты используют изолированную базу данных (`carplanner_test_db`). Строки подключения приходят из Docker Compose; тестовый скрипт лишь задаёт `NODE_ENV=test` и фиксированный `JWT_SECRET` для тестов middleware.

```bash
docker compose run --rm backend npm run test
```

Перед каждым запуском тестовый набор удаляет и пересоздаёт все таблицы (`sequelize.sync({ force: true })`).

### Автоперезагрузка

В контейнере включён `nodemon`. Сохранение файлов в `backend/src` автоматически перезапускает сервер.

## 📡 Документация API (текущее состояние)

Модуль аутентификации полностью реализован и протестирован. Метод входа возвращает подписанный JWT-токен. Защищённые маршруты требуют валидный заголовок `Authorization: Bearer <token>`.

### Публичные эндпоинты

| Метод | Эндпоинт             | Описание                        | Успех       | Ошибки                                           |
| ----- | -------------------- | ------------------------------- | ----------- | ------------------------------------------------ |
| POST  | `/api/auth/register` | Регистрация нового пользователя | 201 Created | 400 (нет обязательных полей), 409 (email занят)  |
| POST  | `/api/auth/login`    | Аутентификация пользователя     | 200 OK      | 401 (неверные учётные данные), 400 (пустое тело) |

**Ответ на вход** содержит JWT-токен:

```json
{
  "data": {
    "user": { "id": 1, "email": "user@example.com" },
    "token": "eyJhbGciOiJIUzI1NiIs..."
  }
}
```

### Защищённые эндпоинты

| Метод | Эндпоинт                 | Описание                          | Успех  | Ошибки                                       |
| ----- | ------------------------ | --------------------------------- | ------ | -------------------------------------------- |
| GET   | `/api/protected/profile` | Возвращает пользователя из токена | 200 OK | 401 (токен отсутствует/недействителен/истёк) |
| POST  | `/api/protected/data`    | Пример авторизованной записи      | 200 OK | 401 (токен отсутствует/недействителен/истёк) |

## 📦 Версионирование и релизы

Проект следует [Semantic Versioning](https://semver.org/) с **пер-компонентными версиями**: бэкенд и фронтенд версионируются и релизятся независимо друг от друга.

- Бэкенд: версия хранится в `backend/package.json`, теги релизов имеют вид `backend-vX.Y.Z`
- Фронтенд: версия хранится в `frontend/pubspec.yaml`, теги релизов имеют вид `frontend-vX.Y.Z`

Релизы автоматизированы с помощью [release-please](https://github.com/googleapis/release-please):

- Коммиты `feat` и `fix`, влитые в `main`, запускают создание Release PR для каждого компонента.
- Мерж Release PR поднимает версию, обновляет `CHANGELOG.md` компонента, ставит тег и создаёт GitHub Release.
- Пока версия в диапазоне `0.x`, ломающие изменения поднимают MINOR; после стабилизации API проект перейдёт на `1.0.0`.

**Схема changelog:**

- `backend/CHANGELOG.md` и `frontend/CHANGELOG.md` генерируются автоматически из Conventional Commits — не редактируйте их вручную.
- Корневой [`CHANGELOG.md`](./CHANGELOG.md) — это рукописная сводка по каждому релизу.

**Никогда не меняйте версии вручную** в `package.json` или `pubspec.yaml` — версия обновляется только Release PR. Подробности о ломающих изменениях и правилах коммитов — в [CONTRIBUTING.md](./CONTRIBUTING.md), раздел «Versioning & Releases».

## 🎯 Управление проектом

Вся работа над проектом отслеживается на доске CarPlanner Sprint Board: https://github.com/users/ViktorAH14/projects/4

**Процесс работы**

Элементы перемещаются по следующим колонкам:

| Колонка     | Значение                           |
| ----------- | ---------------------------------- |
| Backlog     | Новые элементы, ожидающие разбора  |
| To Do       | Приняты в текущий/ближайший спринт |
| In Progress | Активно в работе                   |
| Review      | Pull Request на проверке           |
| Testing     | Реализация проходит проверку       |
| Done        | Завершено (issue закрыт / PR влит) |

**Пользовательские поля**

- **Priority** — срочность элемента.
- **Component** — затронутая часть системы.
- **Estimate (hours)** — оценка трудозатрат в часах.

**Правила автоматизации**

Доска использует встроенные воркфлоу GitHub Projects для поддержания статусов в актуальном состоянии:

- Новые элементы автоматически попадают в колонку **Backlog**.
- Закрытые issue и влитые PR автоматически перемещаются в **Done**.
- Переоткрытые issue автоматически возвращаются в **Backlog** для повторного разбора.
- Если ревьюер запрашивает изменения по PR, его статус возвращается в **In Progress**.
- Закрытые элементы, по которым не было активности в течение месяца, автоматически архивируются, чтобы доска оставалась чистой.
